# مستند مدیریت ساختار نامعتبر فایل LinkedIn

## هدف

فایل `300 user linkedin.txt` در ظاهر یک فایل CSV با ۷۷ ستون است، اما بخشی از ردیف‌های آن از نظر ساختار CSV معتبر نیستند. هدف این مستند توضیح تصمیم‌های فنی برای شناسایی، کنترل و استفاده‌ی امن از این داده‌ها در سیستم جستجو است.

## یافته‌های بررسی فایل

بررسی فایل نشان داد:

- فایل JSON نیست؛ فرمت واقعی آن CSV است.
- فایل دارای ۷۷ ستون است.
- مجموع ردیف‌های خوانده‌شده: ۳۳۶
- ردیف‌های دارای نام قابل استفاده: ۲۹۸
- ردیف‌های حاوی مسیر فایل یا داده‌ی خراب: ۳۸
- تعداد نام‌های یکتا: حدود ۲۶۱

مشکل اصلی این است که بعضی فیلدها دارای comma، quote یا ساختارهای JSON-like هستند، اما به‌صورت صحیح escape یا quote نشده‌اند. در این ردیف‌ها، تعداد ستون‌ها ممکن است همچنان ۷۷ باشد ولی مقدارها از یک نقطه به بعد در ستون اشتباه قرار بگیرند.

برای نمونه، در یک ردیف مقدارهایی مانند موارد زیر مشاهده شد:

- مقدار `phone_numbers` در جایگاه `industry`
- مقدار `job_title` در جایگاه `job_title_role`
- مقدار ایمیل در جایگاه یک فیلد دیگر
- مقدار سابقه یا تاریخ در فیلدهای نامرتبط

بنابراین صرفاً parse شدن ردیف به معنی صحیح بودن mapping آن نیست.

## معماری اصلاح داده

فرآیند import به چهار مرحله تقسیم شده است:

```text
CSV Parser
    ↓
Source Mapper
    ↓
Normalizer / Validator
    ↓
Elasticsearch Bulk Index
```

این جداسازی باعث می‌شود parser مسئول خواندن فایل باشد، mapper مسئول انتخاب فیلدها باشد و normalizer مسئول بررسی کیفیت و نوع داده باشد.

## Source Mapper

Mapper فقط فیلدهای موردنیاز سیستم را انتخاب می‌کند. فیلدهای حساس و غیرضروری مانند موارد زیر وارد Elasticsearch نمی‌شوند:

- `emails`
- `phone_numbers`
- `mobile_phone`
- `work_email`
- آدرس‌های شخصی
- اطلاعات تولد

فیلدهای اصلی قابل استفاده عبارت‌اند از:

- نام و عنوان شغلی
- شرکت و صنعت
- موقعیت مکانی
- سابقه‌ی کاری
- مهارت‌ها
- خلاصه‌ی پروفایل
- تحصیلات و تجربه
- لینک LinkedIn

## Normalizer و اعتبارسنجی

Normalizer پیش از index شدن داده‌ها این کنترل‌ها را انجام می‌دهد:

### فیلدهای عددی

برای `inferred_years_experience`:

- مقدار باید عدد باشد.
- مقدار باید بین صفر و ۱۰۰ باشد.
- مقدارهای نامعتبر حذف می‌شوند، اما کل پروفایل حذف نمی‌شود.

برای `linkedin_connections` نیز فقط مقدار عددی معتبر نگه داشته می‌شود.

### فیلدهای categorical

برای فیلدهای زیر، مقدارهای زیرساختی یا آشکارا اشتباه حذف می‌شوند:

- `industry`
- `location_name`
- `job_company_size`

مقدارهایی که با آرایه، object، شماره تلفن، ایمیل یا تاریخ شروع می‌شوند، گزینه‌ی معتبر فیلتر محسوب نمی‌شوند.

### ردیف‌های غیرپروفایل

ردیف‌هایی که نام آن‌ها مسیر فایل یا شناسه‌ی خطای export است، وارد index نمی‌شوند؛ مانند ردیف‌هایی که با مسیر `H:\...` یا عبارت‌های `part-00001.csv` شروع می‌شوند.

## کنترل خطای Bulk Import

قبلاً پاسخ Elasticsearch Bulk بررسی نمی‌شد و ممکن بود بخشی از رکوردها بدون گزارش خطا index نشوند. اکنون:

1. پاسخ bulk بررسی می‌شود.
2. تعداد itemهای ناموفق استخراج می‌شود.
3. در صورت وجود خطا، import با خطای مشخص متوقف می‌شود.

این کار از نمایش یک نتیجه‌ی ناقص به‌عنوان نتیجه‌ی موفق جلوگیری می‌کند.

## رفتار جستجو

### بدون فیلتر

وقتی `q` و فیلترها خالی باشند، query از نوع `match_all` اجرا می‌شود.

در وضعیت فعلی:

- کل رکوردهای معتبر برگردانده می‌شوند.
- سقف درخواست به ۵۰۰ رکورد افزایش یافته است.
- فایل فعلی ۲۹۸ رکورد معتبر دارد و هر ۲۹۸ رکورد قابل دریافت هستند.
- پروفایل خالی یا `Unnamed profile` نباید در نتیجه وجود داشته باشد.

### جستجوی متنی

فیلد `q` روی این فیلدها جستجو می‌شود:

- `full_name`
- `job_title`
- `skills`
- `summary`
- `job_company_name`

### فیلترها

فیلترهای زیر مستقیماً به فیلدهای Elasticsearch متصل هستند:

| فیلتر UI | پارامتر API | نوع |
| --- | --- | --- |
| Industry | `industry` | exact term |
| Location | `location_name` | exact term |
| Company size | `job_company_size` | exact term |
| Years of experience | `min_years`, `max_years` | numeric range |

گزینه‌های Industry، Location و Company size به‌صورت dynamic از endpoint فیلترها و aggregationهای Elasticsearch دریافت می‌شوند.

## تصمیم‌های UI

به دلیل نبود پشتیبانی واقعی در backend، موارد زیر از UI حذف شده‌اند:

- فیلتر مستقل Job title
- فیلتر مستقل Skills
- Semantic Search
- Save Search
- کنترل‌های نمایشی بدون عملکرد

Job title و Skills همچنان از طریق جستجوی متنی اصلی قابل جستجو هستند، اما به‌عنوان dropdown مستقل نمایش داده نمی‌شوند.

## محدودیت مهم داده

در برخی ردیف‌ها، مشکل فقط نوع داده نیست؛ ترتیب ستون‌ها از ابتدا یا از میانه‌ی ردیف خراب شده است. در این حالت نمی‌توان با اطمینان کامل فهمید مقدار اصلی هر ستون چه بوده است.

بنابراین سیستم دو سیاست دارد:

1. داده‌ی قابل اعتماد را نگه می‌دارد.
2. داده‌ی غیرقابل اعتماد را از فیلترها و فیلدهای حساس حذف می‌کند.

بازسازی کامل این ردیف‌ها فقط در صورتی ممکن است که نسخه‌ی سالم منبع یا schema اصلی export در دسترس باشد.

## پیشنهاد برای نسخه‌ی production

برای محیط production بهتر است import به‌صورت job مستقل اجرا شود و یک گزارش import ذخیره کند، شامل:

- تعداد ردیف‌های خام
- تعداد رکوردهای معتبر
- تعداد ردیف‌های حذف‌شده
- تعداد رکوردهای normalize شده
- تعداد خطاهای Elasticsearch
- فهرست نمونه‌ی خطاها بدون ذخیره‌ی اطلاعات حساس

این گزارش کمک می‌کند کیفیت داده قبل از استفاده‌ی کاربران قابل مشاهده و قابل audit باشد.
